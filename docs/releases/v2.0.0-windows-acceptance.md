## Findings and fixes

Native VM captures exposed clipped settings/sensitive-dialog labels and clipped
review percentages at Windows scaling above 100%. The forms now use a 96-DPI
design baseline, and dynamic layout/owner-drawn column dimensions scale with the
control's actual DPI. Settings, review, sensitive review, and export progress were
exercised at 125% (120 DPI) and 150% (144 DPI), including supported minimum sizes,
button visibility, keyboard focus, and review preview/back navigation.
The Files tab also needed sufficient content height and scrolling at minimum
size. Its last correction was verified by full immediate-parent containment of
the `Specific file names` and `Other folder names` fields, then keyboard focus
into both expanded path-rule inputs.

Export activity continued moving with Windows client-area animation disabled.
Scanning/export indicators now use a stationary continuous style when that
setting is disabled. Three captured export-activity frames had identical SHA-256
hashes at both tested scaling levels after the fix.

The native settings palette harness now retains capture-time window bounds and
rejects stale/out-of-frame pixel samples with a diagnostic. Its existing visual
assertions were retained.

## Outstanding acceptance and publication

- The guest has no audio output device (`waveOutGetNumDevs = 0`). The disabled
  sound guard is covered by native checks, but audible silence was not verified.
- XML export and Windows association dispatch were observed, but the guest's
  existing XML choice led to Windows' app picker. Successful XML viewer opening
  remains unverified; an app picker is not a viewer pass.
- Single-monitor screenshots/focus checks are not complete accessibility or
  mixed-monitor DPI certification. The expired evaluation guest also required
  restarts; temporary harness/provider failures were not counted as product passes.
- All three installers remain `NotSigned`; no code-signing certificate was
  available in the checked Windows certificate stores. Signing and these remaining
  environment checks are required before full release acceptance can be closed.
- At the owner's request, the current unsigned installers were published as
  [GitHub v2.0.0](https://github.com/O-Marmullaku/DumpToTxt/releases/tag/v2.0.0).
  All three public downloads were fetched without authentication through the
  actual npm launcher's downloader and matched the manifest's pinned SHA-256.
  Signature status and VM limitations are disclosed in the release notes.
- On 2026-10-04, npm published `dumptotxt@2.0.0` under `crazyentertainment`
  after staged validation and security-key approval. Its public `latest`
  tarball SHA-1 is `1320c6376dbef3a93a81649d7a931ee19c7e2838`.
  Anonymous checks with empty npm configuration, a fresh cache and a working
  directory outside this repository passed: `npx --yes dumptotxt@latest
  --version`, `--help`, and global installation into an isolated prefix.
  The installed global command returned `2.0.0`; its installer manifest
  exactly matched the approved candidate. These checks did not launch setup;
  end-to-end public `npx` fresh/update installation remains unverified.
  Signing later requires new hashes, re-staging, and a new npm
  version; published manifests must keep their matching installers immutable.

Raw guest results/captures and native captures were retained locally under
`artifacts/checks/vm-acceptance` and `artifacts/checks/ui-final-*`; they are ignored
build/test output. After evidence collection, the guest was restored to its exact
pre-test checkpoint, the test checkpoint was removed, and its state was confirmed
`Off`. The test installation, runtime/viewer additions, and guest preferences were
discarded by that restore.
